01产品概述

把「老师临时要通知一件事」这件小事，做成一条从手机到大屏的可靠链路。

现状是老师在班级群里发消息、或者跑一趟教室口头说，人不在就传不到。本系统让教师在小程序里发一条公告，几秒内出现在目标教室的大屏上，需要时配合语音播报，到期自动消失。

1.1 一句话定位

面向中小学教室的轻量信息投递工具。不替代校园广播系统，也不做内容管理平台，只解决「点对点、短时效、要人看到」的通知。

1.2 核心能力

定向投递

一条公告可投一间教室，也可一次投多个班级。教师在手机上选目标，不涉及复杂的权限树。

三种公告类型

呼叫个人、批量作业、普通通知。类型决定大屏的颜色、排序和是否播报。

可控播报

只有需要「喊人」的公告才播，播 1–2 遍即停，不打扰正常上课。

自动过期

公告带下屏时间，到点自动消失，避免早上的通知挂到下午放学。

1.3 设计原则

  • 教师侧三步内完成。课间站着操作，任何超过三步的流程都会被绕开。
  • 大屏侧永不白屏。断网、服务重启、更新失败，都要有可展示的内容。
  • 服务端不做复杂逻辑。排序、过期判断、播报去重都在客户端完成，服务端只负责存取与广播。
  • 一切可撤回。发错了要能立刻从所有屏幕上消失。

02角色与场景

2.1 角色

角色入口职责与权限
教师微信小程序发布、撤回、重播公告；只能投递到自己任教或有权限的教室
管理员小程序（同一入口，权限更高）维护教室、绑定大屏、导入学生名册、配置教师权限
大屏Windows 客户端无人工操作。展示公告、按规则播报、上报心跳

2.2 三个真实场景走查

场景 A：喊一个学生来办公室

张老师在办公室找李明帮忙搬资料，人不在教室。打开小程序 → 默认选中自己带的班 → 点「呼叫个人」→ 勾选李明 → 输入「到 3 楼办公室」→ 发布。教室大屏顶部滑入一条红色公告，语音播两遍「请李明同学到 3 楼办公室」，40 分钟后自动下屏。

场景 B：通知一批人订正作业

王老师批完作业，有 12 人需要订正。小程序里勾选 12 人，正文只写「午休到 205 订正作业」。大屏显示为橙色公告，名单**不逐条展开**（超过 8 人折叠为「共 12 位同学」），只在名单首位显示前几人，并播报一句汇总提示。

场景 C：常规通知

年级组长发「周五 15:00 家长会」，投给整个年级 8 间教室。大屏显示为灰色常驻条目，不播报，周五 18:00 自动下屏。

2.3 类型对照

type典型内容优先级大屏样式播报

3.2 表结构

PostgreSQL 14+，主键统一 bigserial，时间统一 timestamptz。

-- 学校（单校部署时只有一行，为将来多校预留）
CREATE TABLE schools (
  id          bigserial PRIMARY KEY,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- 教室：一块屏对应一间教室
CREATE TABLE rooms (
  id          bigserial PRIMARY KEY,
  school_id   bigint NOT NULL REFERENCES schools(id),
  name        text NOT NULL,               -- 高三(2)班
  building    text,                        -- 3 号楼
  bind_code   char(6) NOT NULL UNIQUE,     -- 大屏绑定码，管理员生成
  status      text NOT NULL DEFAULT 'active',
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- 设备：装在教室里的 Windows 客户端
CREATE TABLE devices (
  id           bigserial PRIMARY KEY,
  room_id      bigint NOT NULL REFERENCES rooms(id),
  device_no    text NOT NULL UNIQUE,       -- 硬件序列号/机器码
  secret_hash  text NOT NULL,              -- 设备令牌哈希，绑定后下发
  app_version  text,
  last_seen_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_devices_room ON devices(room_id);

-- 班级 / 学生：用于「批量勾选」
CREATE TABLE classes (
  id        bigserial PRIMARY KEY,
  school_id bigint NOT NULL REFERENCES schools(id),
  name      text NOT NULL,
  grade     text
);

CREATE TABLE students (
  id         bigserial PRIMARY KEY,
  class_id   bigint NOT NULL REFERENCES classes(id),
  name       text NOT NULL,
  student_no text,
  UNIQUE (class_id, student_no)
);
CREATE INDEX idx_students_class ON students(class_id);

-- 教师：openid 为微信身份，role 区分教师与管理员
CREATE TABLE teachers (
  id         bigserial PRIMARY KEY,
  school_id  bigint NOT NULL REFERENCES schools(id),
  openid     text NOT NULL UNIQUE,
  name       text NOT NULL,
  phone      text,
  role       text NOT NULL DEFAULT 'teacher',
  created_at timestamptz NOT NULL DEFAULT now()
);

-- 公告主体
CREATE TABLE messages (
  id             bigserial PRIMARY KEY,
  school_id      bigint NOT NULL REFERENCES schools(id),
  teacher_id     bigint NOT NULL REFERENCES teachers(id),
  type           text NOT NULL,             -- call | batch | notice
  title          text NOT NULL,             -- 大屏主标题
  body           text,                      -- 副内容，可空
  priority       smallint NOT NULL DEFAULT 0, -- 1 置顶，0 普通
  start_at       timestamptz NOT NULL DEFAULT now(),
  expire_at      timestamptz NOT NULL,
  broadcast_times smallint NOT NULL DEFAULT 0, -- 0 = 只展示不播
  status         text NOT NULL DEFAULT 'active', -- active | revoked
  client_token   text UNIQUE,               -- 幂等键，防重复提交
  created_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_messages_active ON messages(status, expire_at);
CREATE INDEX idx_messages_teacher ON messages(teacher_id, created_at DESC);

-- 公告投递到哪些教室
CREATE TABLE message_rooms (
  message_id bigint NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  room_id    bigint NOT NULL REFERENCES rooms(id),
  PRIMARY KEY (message_id, room_id)
);
CREATE INDEX idx_mr_room ON message_rooms(room_id);

-- 播报审计（客户端本地也有一份，服务端仅用于排查）
CREATE TABLE broadcast_logs (
  id         bigserial PRIMARY KEY,
  device_id  bigint NOT NULL REFERENCES devices(id),
  message_id bigint NOT NULL,
  round      smallint NOT NULL,
  played_at  timestamptz NOT NULL DEFAULT now()
);
为什么 message_rooms 单独建表：一条公告投 8 个班是常见操作。存成逗号分隔的字段后，「某间教室当前该显示哪些公告」这个最热的查询就没法走索引了。

3.3 状态定义

公告只有两个持久状态，其余展示状态由客户端根据时间推导：

状态来源说明
active数据库有效记录，是否该展示由 start_at / expire_at 判断
revoked数据库教师主动撤回，任何端都不再展示，但保留记录便于审计
pending客户端推导now < start_at，尚未到生效时间，不展示
expired客户端推导now >= expire_at，本地移除，不依赖服务端推送

单机部署即可支撑几十到几百间教室：一条公告产生的广播是内存操作，瓶颈不在 Node 的并发能力，而在教室网络的稳定性。

4.2 技术选型

层选型理由
大屏Electron + Vue 3 / React前端技术栈复用，全屏 kiosk、自动更新、开机自启都有成熟方案；TTS 通过主进程调用系统语音
大屏（备选）C# WPF若团队是 .NET，System.Speech 调本地语音最直接，无需额外依赖
服务端Node.js 20 + Fastify与前端同语言，WebSocket 生态成熟；ws 库足够，不必引入 Socket.IO
数据库PostgreSQL 14+时间区间查询、部分索引好用；数据量小，无需缓存层
小程序原生（WXML/WXSS）页面不超过 5 个，引入框架反而增加构建复杂度
部署Docker Compose + Nginx单机可维护；域名复用已有 ICP 备案主体

4.3 部署形态

                    ┌──────────────────────────────┐
   小程序  ──HTTPS──▶│  Nginx  (api.xxx.com:443)    │
                    │   ├─ /api/*   → Node:3000    │
                    │   └─ /ws      → Node:3000    │
                    └──────────────┬───────────────┘
                                   │
                          ┌────────▼────────┐
                          │  PostgreSQL 14  │

域名要求：必须 HTTPS + WSS，且域名已完成 ICP 备案、备案主体与小程序主体一致。Nginx 需开启 TLS 1.2 及以上，证书链完整（安卓真机对中间证书缺失很敏感）。

5.2 REST 接口清单

方法路径说明

幂等实现：client_token 建唯一索引。重复提交时捕获唯一键冲突，直接返回已存在的那条记录，不重复广播。这比在应用层查一次再插更可靠——并发下不会有竞态窗口。

大屏绑定

POST /api/devices/bind
{ "bindCode": "483920", "deviceNo": "KIOSK-3F-201" }

// 200 OK
{

bindCode 由管理员在后台为每间教室生成，6 位数字，只用于首次绑定，绑定成功后作废该码并换发设备令牌。设备令牌写入本地加密存储，重装系统需重新绑定。

快照

GET /api/device/snapshot

{
  "code": 0,
  "data": {
    "serverTime": "2026-10-21T15:31:02+08:00",
    "room": { "id": 12, "name": "高三(2)班" },
    "messages": [
      {
        "id": 1024,
        "type": "call",
        "title": "李明 · 到 3 楼办公室",
        "priority": 1,
        "startAt": "2026-10-21T15:30:00+08:00",

必须返回 serverTime：教室电脑的时钟经常错几十分钟，客户端拿它和本地时间求差值，后续所有「到期下屏」都用校正后的时间判断，否则公告会提前消失或长期不下屏。

5.3 WebSocket 协议

地址
wss://api.example.com/ws/device?token=<deviceToken>
心跳
客户端每 30s 发 ping，服务端回 pong；90s 无数据判定断线
重连
指数退避 1s → 2s → 4s → 8s → 16s，上限 30s，加 0–500ms 抖动
顺序
服务端保证单连接内事件有序；客户端按 ts 丢弃乱序的旧事件

服务端 → 客户端

// 新公告
{ "event": "message.created", "ts": 1761029404000, "data": { /* 同快照中的 message 结构 */ } }

// 内容或时间被修改
{ "event": "message.updated", "ts": 1761029500000, "data": { /* 完整对象，客户端整体替换 */ } }

// 撤回
{ "event": "message.revoked", "ts": 1761029600000, "data": { "id": 1024 } }

// 重播指令（只播不复读，不改变列表）
{ "event": "message.replay", "ts": 1761029700000, "data": { "id": 1024, "times": 2 } }

// 服务端要求重新拉快照（如数据修复后）
{ "event": "force.resync", "ts": 1761029800000, "data": {} }

客户端 → 服务端

{ "event": "ping", "ts": 1761029900000 }
{ "event": "ack", "data": { "messageId": 1024, "round": 1 } }
本系统没有「事件补齐」接口，只有快照。断线期间的事件一律丢弃，重连成功后强制走一次快照。原因：公告是「当前状态」而非「操作流」，补事件会引入复杂的序号管理，而全量快照在这个数据量下只要几毫秒。

code含义处理建议

6.2 视觉规范

项目规格说明
安全边距左右 64px，上下 56px电视过扫描会裁掉边缘，内容不能贴边
教室名38px / 500放左上，远距离也能确认是哪间教室
公告标题36px / 400，行高 1.3超过 2 行截断，完整内容在详情里看
元信息22px，次要色发布时间、播报轮次、剩余时间
单屏容量最多 3–5 条第 4 条起降为紧凑样式，第 6 条折叠为「还有 N 条」
类型色call #C0392B / batch #C08A2E / notice #CFCCC2只用于左边框与徽标，不整块铺色，避免刺眼
新公告动效顶部滑入 280ms，ease-out播报期间整条做一次轻微高亮，不做循环闪烁
为什么不铺深色背景：教室投影和电视普遍偏亮、对比度差，深底白字在廉价面板上会发灰。浅底深字 + 单一强调色在实测中更清晰，也减少长时间常亮的视觉压迫。

6.3 排序与折叠规则

  1. 先按 priority 降序（置顶优先）。
  2. 再按类型权重：call 3 > batch 2 > notice 1。
  3. 最后按 createdAt 倒序（新的在上）。
  4. 过滤掉 now < startAt 与 now >= expireAt 的条目。
  5. 超过 5 条时，前 4 条正常渲染，第 5 行固定显示「还有 N 条公告」。

6.4 播报队列

语音是这类系统最容易翻车的地方。三条硬规则：

  • 串行播放。用单消费者队列，一条播完再播下一条，绝不叠音。
  • 去重按键为 messageId + round。已播过的轮次写入本地表，重连、重放、服务端重复推送都不会再念一遍。
  • 可被打断。新来的 call 类型公告优先级更高，立即中止当前播报并插队；notice 不参与播报。
// 本地播报记录，用于断电重启后不重播
CREATE TABLE local_broadcast (
  message_id  INTEGER NOT NULL,
  round       INTEGER NOT NULL,
  played_at   INTEGER NOT NULL,
  PRIMARY KEY (message_id, round)
);

播报文本拼接规则：请 + 姓名 + 到 + 地点；批量类型使用汇总句「请以下 N 位同学到 205 办公室」，不逐个人名朗读——12 个名字念完要 40 秒，教室已经吵翻了。

6.5 连接与降级

状态界面表现行为
connecting右上角灰点显示本地缓存内容，不做任何提示音
online绿点 + 时间正常收事件
reconnecting黄点「重连中」指数退避重连，期间继续展示缓存

6.6 Kiosk 七件套

教室电脑是被忽略的重灾区：会休眠、会弹更新、会被学生按 Alt+F4。以下七项必须在安装包里做掉，不能靠现场配置。

  • 开机自启（注册表 Run 或启动文件夹），无需登录桌面即可拉起
  • 全屏无边框 + 置顶，屏蔽 Alt+F4、Win 键、任务管理器快捷键
  • 鼠标指针隐藏，60 秒无操作自动熄屏光标
  • 禁止系统休眠与屏保（调用 SetThreadExecutionState）
  • 看门狗：主进程崩溃后 5 秒内由守护进程重新拉起
  • 版本更新失败自动回滚到上一可用版本
  • 本地缓存兜底：启动时先渲染缓存再连网，保证不白屏

交互约束 类型决定默认值：选「呼叫个人」自动带 2 遍播报、40 分钟下屏；选「通知」自动关闭播报、下屏时间设为当天 22:00。

为什么单页不分步 老师课间只有两三分钟。分步表单会让人中途退出，单页滚动一屏内解决，且默认值已经把 80% 的填写工作省掉。

发布后立刻给反馈 成功页显示「已投递到 1 块屏」，而不是简单的「发布成功」——老师需要确认到底有没有送到。

7.3 登录与身份

使用 wx.login 拿 code 换取 openid，服务端按 openid 查教师表：

  • 命中 → 直接登录，返回令牌与权限范围。
  • 未命中 → 显示「你的微信尚未被学校管理员添加」，附管理员联系方式，不开放自助注册。
为什么不做注册：这个系统里「能发公告」等于「能对全教室喊话」，必须由学校侧白名单控制。开放注册会直接导致内容事故。

7.4 内容安全

发布前必须调用微信 security.msgSecCheck 检测正文，命中违规词直接拦截并提示修改。这一步不是可选项：一旦有敏感内容出现在教室大屏上，小程序可能被整体下架。

POST https://api.weixin.qq.com/wxa/msg_sec_check?access_token=ACCESS_TOKEN
{ "content": "到 3 楼办公室", "version": 2, "scene": 2, "openid": "oXXXX" }

access_token 必须由服务端缓存（有效期 7200s，提前 5 分钟刷新），绝不能在小程序端请求——AppSecret 一旦泄漏，整个账号的接口都可以被冒用。

8.2 断线重连

连接断开
  → 界面切「重连中」，继续展示缓存
  → 退避等待（1s/2s/4s ... 上限 30s + 抖动）
  → 重连成功
  → GET /device/snapshot（拿全量 + serverTime）
  → 用快照整体替换内存列表（不是合并）
  → 播放队列中尚未播完的轮次继续
  → 界面切「在线」
必须整体替换，不能合并。断线期间可能发生过撤回，合并逻辑会把已撤回的公告又留在屏幕上。快照即真相。

8.3 撤回

教师点撤回 → 服务端把 status 置为 revoked → 向该公告涉及的所有在线设备推 message.revoked → 客户端从列表移除，若正在播报则立即停止。

离线设备不会收到推送，但下次拉快照时不会再包含该公告，因此不需要额外的补偿机制。

8.4 过期下屏

客户端每 1 秒检查一次列表，把 now >= expireAt 的条目移除。这里不依赖服务端——服务端推送可能延迟、可能丢，而屏幕上的时间必须准确。所有时间比较都使用校正后的服务器时间偏移量。

09非功能与合规

9.1 性能指标

指标目标值说明
推送延迟 P95< 1s从接口返回成功到屏幕出现
单机并发连接≥ 1000一所学校通常 30–80 间教室，留足余量
快照接口< 100ms单教室有效公告通常不超过 10 条
冷启动到出画面< 3s读本地缓存优先
长稳运行30 天无重启内存泄漏是主要风险，需跑 72h 压测

9.2 安全

  • AppSecret 只存在服务端环境变量，永不进入小程序代码或日志。
  • 设备令牌与教师令牌分离，设备令牌只能访问本教室数据，越权直接 403。
  • 创建公告做频率限制：同一教师 60s 内最多 10 条，防误触连点与刷屏。
  • 所有写接口校验 roomIds 是否在教师权限范围内，不能只信前端。

M1 · 第 1–2 周
链路打通

可上线
kiosk 七件套、安装包与自动更新、看门狗、监控告警、压测（72h 长稳）、备案与类目资质、提审。同期完成部署脚本与运维手册。

工作量粗估：服务端 8–10 人日，大屏 12–15 人日，小程序 7–9 人日，测试与部署 5 人日。合计约 32–39 人日，按 2 人并行折算 5–6 周。
